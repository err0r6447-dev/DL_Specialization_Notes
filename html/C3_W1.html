1. Why ML Strategy?

🟢 Intuition Building a deep-learning system is not just about picking a network architecture. It is about making many small decisions in the right order, so that each experiment actually moves you closer to a working product.

1.1 The motivating example

Imagine you are building a cat classifier — a system that looks at a photo and decides whether it contains a cat. Your first model gets about 90% accuracy. You want it to be much better. What do you do?

Andrew Ng lists a whole menu of ideas that a team might try:

  • Collect more data.
  • Collect a more diverse training set (e.g., cats in different poses, lighting, backgrounds).
  • Train the algorithm longer with gradient descent.
  • Try Adam instead of plain gradient descent.
  • Try a bigger network.
  • Try a smaller network.
  • Add dropout.
  • Add \(L_2\) regularization.
  • Change the network architecture (e.g., activation functions, number of hidden units).
🟡 Important All of these ideas are individually reasonable. The problem is that they pull in different directions. If you try them at random, you can spend months and end up worse than where you started. ML strategy is the discipline of choosing which idea to try next, based on evidence, instead of guessing.

1.2 What "strategy" actually means here

Strategy in this course means:

  1. Define a clear goal — a single number you want to improve.
  2. Diagnose where your model is failing (bias? variance? bad data? bad metric?).
  3. Choose the right tool for that specific failure mode.

The rest of this week is essentially a toolkit for steps 1–3.

🔵 Definition Machine Learning Strategy — the set of principles and practices for deciding what to do next in an ML project, so that engineering effort is spent on the changes most likely to improve the final product.

2. Orthogonalization

🔵 Definition Orthogonalization — designing your system (and your tuning process) so that each control affects exactly one aspect of performance, without interfering with the others.

2.1 The TV-tuning analogy

Think of an old television set with separate physical knobs:

  • One knob moves the picture up and down.
  • One knob moves the picture left and right.
  • One knob changes the size (zoom).
  • One knob changes the shape (skew).

Each knob does one thing. If the picture is too far to the right, you turn the horizontal knob — you do not have to re-tune the vertical position, the size, or the shape. The controls are orthogonal: turning one does not disturb the others.

2.2 Why orthogonalization matters in ML

In deep learning, the "knobs" are things like:

  • Network size / depth
  • Learning rate and optimizer
  • Regularization strength (dropout, \(L_2\))
  • Training set size and diversity
  • Data augmentation
  • Architecture family (CNN, RNN, Transformer)

If your controls are not orthogonal — for example, if increasing model size also makes training unstable, or if adding regularization also slows convergence — then every experiment becomes a guess, and it becomes very hard to know what to change next.

🟢 Intuition Orthogonalization is the difference between a well-organized toolbox and a drawer full of tangled cables. With a tangled drawer, pulling one cable moves five others. With an orthogonal toolbox, you pick exactly the tool you need.
🔴 Warning Orthogonalization is an ideal, not always a reality. Real deep-learning systems have coupled controls (e.g., changing architecture can affect both bias and variance). The goal is to design your process so that, as much as possible, you are tuning one thing at a time.

3. The Chain of Assumptions in ML

Andrew Ng presents a four-step "chain" that a machine-learning project must satisfy. Each step has its own failure mode and its own set of remedies.

3.1 Step 1 — Fit the training set well

What it means: the model should achieve low error on the data it was trained on.
If it fails: the model is underfitting (high bias). Remedies: a bigger network, a better optimization algorithm (e.g., Adam), training longer, or a different architecture.

3.2 Step 2 — Fit the dev set well

What it means: the model should also do well on a held-out development set that it never trained on.
If it fails: the model is overfitting (high variance). Remedies: regularization, more training data, data augmentation.

3.3 Step 3 — Fit the test set well

What it means: the model should do well on a final, untouched test set that represents the real distribution.
If it fails: your dev set was too small or not representative. Remedy: a bigger dev set (or a better-designed dev set).

3.4 Step 4 — Perform well in the real world

What it means: the model should actually help users (e.g., show cat lovers more cats without showing them inappropriate images).
If it fails: your metric or your dev/test set is not measuring the right thing. Remedy: change the metric or the dev/test set.

🟡 Important The chain is a diagnostic order. Always check step 1 before step 2, step 2 before step 3, and step 3 before step 4. Skipping ahead wastes time.

4. Single Number Evaluation Metric

🔵 Definition A single-number evaluation metric is one number that summarizes the quality of a model, so that any two models can be compared with a simple "is this number better or worse?" test.

4.1 The problem: too many numbers

Suppose you have two classifiers, A and B, and you measure both precision and recall. You get:

ClassifierPrecisionRecall
A95%90%
B98%85%

Which one is better? A has higher recall; B has higher precision. With two numbers, there is no clear winner. You cannot tell your team "use the better one" — you have to argue. This slows down iteration.

🟢 Intuition A single-number metric is like a scoreboard. In a sport, you do not compare teams by "goals scored" and "goals conceded" separately — you have a points system that combines them. A single-number metric is that points system for your model.

4.2 Precision and Recall — the building blocks

First, the confusion matrix for a binary classifier (e.g., cat vs. non-cat):

Actual class \(y\)
1 (cat)0 (no cat)
Predicted \(\hat{y}\)1 (cat)True Positive (TP)False Positive (FP)
0 (no cat)False Negative (FN)True Negative (TN)
🔵 Definition — Precision Of all the examples the model predicted as positive, what fraction were actually positive?
\[ \text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}} \times 100\% \]
TP = true positives, FP = false positives. A high precision means: when the model says "cat", it is usually right.
🔵 Definition — Recall Of all the examples that actually were positive, what fraction did the model correctly identify?
\[ \text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}} \times 100\% \]
FN = false negatives. A high recall means: the model rarely misses a real cat.
🟣 Example — Cat classifier Suppose 100 images contain cats and 900 do not. The model predicts "cat" for 80 of the 100 cat images and for 20 of the 900 non-cat images.
  • TP = 80, FN = 20, FP = 20, TN = 880
  • Precision = 80 / (80 + 20) = 80%
  • Recall = 80 / (80 + 20) = 80%
Precision answers "when we say cat, how often are we right?" Recall answers "of all the cats, how many did we find?"

4.3 Combining them: the F1 score

Precision and recall are often in tension. A model that predicts "cat" only when it is extremely confident can have very high precision but low recall. A model that predicts "cat" very aggressively can have high recall but low precision.

The F1 score combines them into one number using the harmonic mean:

\[ F_1 = \frac{2}{\frac{1}{P} + \frac{1}{R}} \]
\(P\) = precision, \(R\) = recall. The harmonic mean punishes extreme imbalance: if either P or R is very low, F1 is pulled down.

Why harmonic mean instead of ordinary average? Because the harmonic mean is closer to the smaller of the two numbers. If P = 98% and R = 10%, the arithmetic mean is 54% (looks okay), but the harmonic mean is about 18% (correctly shows the model is bad).

🟣 Example — F1 in action
ClassifierPrecisionRecallF1
A95%90%92.4%
B98%85%91.0%

F1 says A is better. With two numbers you could argue forever; with one number you can decide.

🟡 Important F1 is not the only possible single-number metric. You could also use the arithmetic average, a weighted average, or any custom formula. The key requirement is that it must rank-order models the same way your real-world goal does.

4.4 Another example: multi-region accuracy

Suppose your cat classifier is deployed in four regions and you measure error in each:

AlgorithmUSChinaIndiaOtherAverage
A3%7%5%9%6.0%
B5%6%5%10%6.5%
C2%3%4%5%3.5%

With four numbers per algorithm, comparison is hard. By taking the average across regions, you get one number per algorithm and can rank them immediately. This is another form of a single-number evaluation metric.

🔴 Warning — Choosing the average wisely A simple average assumes every region is equally important. If your product is used mostly in the US, you might want a weighted average that puts more weight on US performance. The metric must reflect what you actually care about.

5. Satisficing & Optimizing Metrics

🔵 Definition — Optimizing metric The optimizing metric is the one number you want to make as good as possible (maximize accuracy, minimize error).
🔵 Definition — Satisficing metric A satisficing metric is a metric that just has to meet a threshold — it does not need to be optimized further.

5.1 The classifier example

ClassifierAccuracyRunning time
A90%80 ms
B92%95 ms
C95%1500 ms

Suppose the product requirement is: running time must be under 100 ms.

  • Accuracy is the optimizing metric — we want it as high as possible.
  • Running time is the satisficing metric — it just has to be < 100 ms.

Classifier C has the best accuracy but fails the running-time requirement, so it is out. Between A and B, B is better on accuracy and still satisfies running time, so B wins.

🟢 Intuition Think of buying a laptop. You want the best battery life possible (optimizing), but you also need the price to be under a budget (satisficing). You do not optimize price to zero — you just need it to be acceptable.

5.2 The general rule

\[ N_{\text{metric}} : \begin{cases} 1 & \text{Optimizing metric} \\ N_{\text{metric}} - 1 & \text{Satisficing metrics} \end{cases} \]
If you have \(N\) metrics, pick exactly one to optimize, and let the rest be satisficing (must meet thresholds). This turns a multi-objective problem into a single-objective one.
🟡 Important Without this discipline, teams end up with a "scoreboard" of five numbers that conflict. By designating one optimizing metric, everyone knows exactly what "better" means.

6. Train / Dev / Test Distributions

🔵 Definition The distribution of a dataset is the statistical pattern of the data — what kinds of examples appear, how often, and in what proportions.

6.1 The core guideline

🟡 Guideline Choose your dev set and test set to reflect the data you expect to get in the future, and that you consider important to do well on.

This is one of the most important practical lessons in the course. If your dev set does not look like the data your model will see in production, then improving dev performance will not improve real-world performance.

6.2 A cautionary example: loan approvals

A team built a model to predict loan repayment for medium-income zip codes. They randomly split their data into train/dev/test. The dev set happened to contain mostly medium-income examples. The model looked great on dev — but when deployed to low-income zip codes, it failed badly.

🔴 Warning Randomly shuffling your data into train/dev/test is only correct if the data is already representative of what you care about. If your data comes from many sources with different proportions, random shuffling can produce a dev set that does not match your target.

6.3 How to fix it

  • Make the dev and test sets come from the same distribution.
  • Make that distribution match the future deployment data.
  • If you have data from multiple regions, you may need to re-weight or re-sample so the dev set reflects your priorities.

7. Size of Dev and Test Sets

7.1 The old way (small data)

When datasets were small (hundreds to thousands of examples), the common splits were:

  • 70% train / 30% test
  • 60% train / 20% dev / 20% test

7.2 The modern way (big data)

With millions of examples, you do not need 20–30% for dev/test. You can use a much smaller fraction and still have a statistically meaningful dev/test set:

  • 98% train / 1% dev / 1% test
  • Or even 99.5% train / 0.25% dev / 0.25% test

7.3 Guidelines for sizing

  • Dev set: big enough to detect differences between the models you are trying. If two models differ by 0.1% and your dev set has only 100 examples, you cannot tell them apart. If the difference you care about is 0.1%, you need roughly 10,000+ dev examples.
  • Test set: big enough to give high confidence in the final performance of your system. Typically similar in size to the dev set.
🟣 Example — Why dev set size matters You have a dev set of 100 examples. Model A gets 97% correct, Model B gets 97.1%. The difference is one example. That is not statistically meaningful — you cannot trust it. With 10,000 examples, the same 0.1% difference corresponds to 10 examples, which is much more reliable.
🟡 Important The "no test set" pattern: in some applications (e.g., online advertising), you may decide not to keep a separate test set and instead use the dev set as your final evaluation. This is acceptable when the cost of a wrong decision is low and you have plenty of data — but it removes your unbiased final check.

8. When to Change Dev/Test Sets & Metrics

8.1 The pornographic-image example

A team builds a cat classifier to show cat images to cat lovers. They measure classification error:

AlgorithmClassification error
A3%
B5%

By the metric, A is better. But in production, Algorithm A occasionally lets pornographic images through. Algorithm B makes more mistakes overall, but never shows inappropriate content.

From the company's and users' perspective, B is the better algorithm. The metric failed to rank-order the two algorithms according to what actually matters.

🟡 Guideline If doing well on your metric + dev/test set does not correspond to doing well on your application, change your metric and/or your dev/test set.

8.2 The weighted-error metric

The standard misclassification error is:

\[ \text{Error} = \frac{1}{m_{\text{dev}}} \sum_{i=1}^{m_{\text{dev}}} \mathcal{L}\{\hat{y}^{(i)} \neq y^{(i)}\} \]
\(m_{\text{dev}}\) = number of dev examples.
\(\hat{y}^{(i)}\) = model prediction for example \(i\).
\(y^{(i)}\) = true label for example \(i\).
\(\mathcal{L}\{\hat{y} \neq y\}\) = 1 if the prediction is wrong, 0 if it is right.
This just counts the fraction of misclassified examples.

The problem: this metric treats a pornographic image exactly the same as a misclassified cat. We need to weight the errors.

\[ \text{Error} = \frac{1}{\sum_i w^{(i)}} \sum_{i=1}^{m_{\text{dev}}} w^{(i)} \, \mathcal{L}\{\hat{y}^{(i)} \neq y^{(i)}\} \]
\(w^{(i)}\) = weight for example \(i\). Setting \(w^{(i)} = 1\) for most examples and \(w^{(i)} = 10\) (or more) for pornographic images makes the metric punish those mistakes much more heavily.
🟣 Example — Weighting Suppose 1% of dev images are pornographic. With uniform weights, a model that misclassifies all of them still only loses 1% on the metric. With weight 10 on pornographic images, that same model loses much more — the metric now reflects the real cost.

8.3 The two-step process

  1. Define a metric that correctly rank-orders classifiers according to your real preferences.
  2. Optimize that metric as well as you can.
🟢 Intuition Step 1 is like deciding what game you are playing (what counts as a win). Step 2 is actually playing it. If you skip step 1, you might win the wrong game perfectly.

9. Why Human-Level Performance?

🔵 Definition — Bayes optimal error The Bayes optimal error (or Bayes error) is the best possible error any function from \(x\) to \(y\) can achieve. It is a theoretical lower bound — no model can do better.

9.1 The performance curve

The slides show a graph with accuracy on the vertical axis and time on the horizontal axis. There are three horizontal lines:

  • Bayes optimal error — the highest possible accuracy (red dashed line).
  • Human-level performance — a blue dashed line below it.
  • Machine learning — a solid curve that starts low and rises over time.

9.2 Why ML slows after surpassing humans

Two main reasons:

  1. Humans are often close to Bayes optimal. For natural perception tasks (recognizing a cat, transcribing speech), the best human performance is near the theoretical ceiling. There is little room left above it.
  2. The tools we use below human level stop working above it. While ML is worse than humans, you can:
    • Get more labeled data from humans.
    • Do manual error analysis: "why did the human get this right?"
    • Use human performance as a proxy for Bayes error to analyze bias/variance.
    Once ML surpasses humans, these tools become much harder to use.
🟡 Important Human-level performance is useful mainly as a proxy for Bayes error. It gives you a target to aim for and a reference point for diagnosing whether your model is suffering from bias or variance.

10. Avoidable Bias

🔵 Definition — Avoidable bias Avoidable bias is the gap between the human-level error (as a proxy for Bayes error) and the training error. It is the part of the bias you can actually reduce by improving your model.
\[ \text{Avoidable bias} \approx \text{Human-level error} - \text{Training error} \] \[ \text{Variance} \approx \text{Training error} - \text{Dev error} \]

10.1 The cat classification example

Scenario AScenario B
Human error (≈ Bayes)1%7.5%
Training error8%8%
Dev error10%10%

Scenario A:

  • Avoidable bias = 1% − 8% = 7% (large)
  • Variance = 8% − 10% = 2% (smaller)
  • Diagnosis: high avoidable bias. Focus on bias-reduction techniques (bigger network, train longer, better optimizer).

Scenario B:

  • Avoidable bias = 7.5% − 8% = 0.5% (small)
  • Variance = 8% − 10% = 2% (larger)
  • Diagnosis: high variance. Focus on variance-reduction techniques (more data, regularization).
🟢 Intuition Think of a student preparing for an exam. The "human-level" score is 95%. If the student scores 70% on practice questions, the gap (25%) is avoidable bias — they need to study more. If they score 94% on practice but only 80% on the real exam, that is variance — they memorized practice problems instead of learning the material.

11. Understanding Human-Level Performance

🔵 Definition "Human-level error" is not one number. It depends on which human you are talking about — a typical person, a typical doctor, an experienced doctor, or a team of experienced doctors.

11.1 Medical image classification example

WhoClassification error
Typical human3.0%
Typical doctor1.0%
Experienced doctor0.7%
Team of experienced doctors0.5%

Which one is "human-level"? It depends on the purpose:

  • If you are trying to replace a typical doctor, 1.0% is your reference.
  • If you are trying to beat the best team, 0.5% is your reference.
  • The Bayes error is at most 0.5% (the best human result), possibly lower.
🟡 Important Choose the human-level reference that matches your application goal. Using the wrong reference will mislead your bias/variance diagnosis.

11.2 Error analysis example

Scenario AScenario BScenario C
Human (proxy for Bayes)1%1%0.5%
Training error5%1%0.7%
Dev error6%5%0.8%

Scenario A: Avoidable bias = 4–4.5%, variance = 1%. → Focus on bias reduction.

Scenario B: Avoidable bias = 0–0.5%, variance = 4%. → Focus on variance reduction.

Scenario C: Human error must be ≤ 0.5% (otherwise training error 0.7% would be below it, which is impossible if human error is a proxy for Bayes). Avoidable bias = 0.2%, variance = 0.1%. → Focus on bias reduction.

🔴 Warning If your training error is lower than your human-level reference, then your human-level reference is not a good proxy for Bayes error. Either the model is overfitting the training set, or the human reference is not actually the best achievable.

12. Surpassing Human-Level Performance

Scenario AScenario B
Team of humans0.5%0.5%
One human1.0%1.0%
Training error0.6%0.3%
Dev error0.8%0.4%

Scenario A: Bayes error ≈ 0.5%. Avoidable bias = 0.1%, variance = 0.2%. The model is close to human level; both bias and variance are small.

Scenario B: Training error 0.3% is below the team-of-humans error 0.5%. There is not enough information to know whether bias or variance reduction is needed. It does not mean the model cannot improve — it means the conventional diagnostic tools are less reliable.

🟡 Important — Where ML surpasses humans ML tends to surpass human-level performance on problems involving structured data rather than natural perception:
  • Online advertising
  • Product recommendations
  • Logistics (predicting transit time)
  • Loan approvals
These are problems where there is a lot of data and the patterns are statistical, not perceptual.

13. Improving Your Model Performance

13.1 The two fundamental assumptions

  1. Low avoidable bias — you can fit the training set well.
  2. Low variance — training performance generalizes well to dev/test.

13.2 The diagnostic rule

\[ \text{If } (\text{Human error} - \text{Training error}) > (\text{Training error} - \text{Dev error}) \] \[ \Rightarrow \text{Focus on bias reduction} \] \[ \text{If } (\text{Training error} - \text{Dev error}) > (\text{Human error} - \text{Training error}) \] \[ \Rightarrow \text{Focus on variance reduction} \]

13.3 The toolkit

🟡 Important These are not mutually exclusive. In practice, you often alternate: reduce bias, then reduce variance, then reduce bias again. The diagnostic rule tells you which problem is currently the bottleneck.

14. Weekly Summary

🔵 Key Concepts
  • Orthogonalization — design controls so each affects one thing.
  • Chain of assumptions — train → dev → test → real world; diagnose in order.
  • Single-number metric — one number to rank models (e.g., F1).
  • Satisficing vs. optimizing — one metric to optimize, others to satisfy.
  • Dev/test distributions — must match future deployment data.
  • Dev/test sizes — large enough to detect differences; 1% of big data is fine.
  • Metric changes — if the metric does not match the application, change it.
  • Human-level performance — proxy for Bayes error.
  • Avoidable bias — human error − training error.
  • Variance — training error − dev error.

Important Equations

EquationMeaning
\(\text{Precision} = \frac{TP}{TP+FP}\)Of predicted positives, how many are correct.
\(\text{Recall} = \frac{TP}{TP+FN}\)Of actual positives, how many were found.
\(F_1 = \frac{2}{1/P + 1/R}\)Harmonic mean of precision and recall.
\(\text{Avoidable bias} = \text{Human error} - \text{Training error}\)How much bias you can still remove.
\(\text{Variance} = \text{Training error} - \text{Dev error}\)How much the model fails to generalize.

Common Confusions

  • Bias vs. variance: bias = underfitting (training error high); variance = overfitting (dev error much higher than training).
  • Precision vs. recall: precision is about false positives; recall is about false negatives.
  • Optimizing vs. satisficing: one metric to maximize; others just need to meet a threshold.
  • Human-level vs. Bayes error: human-level is a proxy, not the true Bayes error.
  • Dev set vs. test set: dev is for iterating; test is for final unbiased evaluation.

15. Quick Review (with answers)

Q1: What is orthogonalization in the context of ML?
Designing your system so that each control (hyperparameter, data change, architecture change) affects exactly one aspect of performance, without interfering with others. Like separate knobs on a TV.
Q2: List the four steps of the chain of assumptions in ML.
1. Fit the training set well. 2. Fit the dev set well. 3. Fit the test set well. 4. Perform well in the real world.
Q3: What is the difference between precision and recall?
Precision = TP/(TP+FP): of all predicted positives, how many are correct. Recall = TP/(TP+FN): of all actual positives, how many were found.
Q4: Why is F1 a better single-number metric than the arithmetic mean of precision and recall?
The harmonic mean (F1) is pulled toward the smaller of the two values, so it penalizes extreme imbalance. The arithmetic mean can look acceptable even if one value is very low.
Q5: What is a satisficing metric?
A metric that only needs to meet a threshold — it does not need to be optimized further. Example: running time must be under 100 ms.
Q6: What is the guideline for choosing dev/test sets?
Choose them to reflect the data you expect to get in the future and consider important to do well on. They should come from the same distribution.
Q7: In the modern era of big data, what split is common?
98% train / 1% dev / 1% test (or similar). Even 1% of millions of examples is large enough for evaluation.
Q8: When should you change your evaluation metric?
When doing well on the metric + dev/test set does not correspond to doing well on your application (e.g., the pornographic-image example).
Q9: What is Bayes optimal error?
The best possible error any function from x to y can achieve. It is a theoretical lower bound.
Q10: What is avoidable bias?
The gap between human-level error (proxy for Bayes error) and training error. It is the part of bias you can still reduce.
Q11: If training error is 8%, dev error is 10%, and human error is 1%, what should you focus on?
Avoidable bias = 1% − 8% = 7%. Variance = 8% − 10% = 2%. Since avoidable bias > variance, focus on bias reduction.
Q12: If training error is 8%, dev error is 10%, and human error is 7.5%, what should you focus on?
Avoidable bias = 7.5% − 8% = 0.5%. Variance = 8% − 10% = 2%. Since variance > avoidable bias, focus on variance reduction.
Q13: Why does ML progress slow down after surpassing human-level performance?
Because human performance is often close to Bayes optimal (little room above), and the tools we use below human level (human labeling, manual error analysis, bias/variance analysis) become harder to use.
Q14: Give two examples of problems where ML significantly surpasses human-level performance.
Online advertising, product recommendations, logistics (predicting transit time), loan approvals. These involve structured data rather than natural perception.
Q15: What are the two fundamental assumptions of supervised learning?
1. You can fit the training set pretty well (low avoidable bias). 2. The training set performance generalizes well to dev/test (low variance).
Q16: Name three bias-reduction techniques.
Train a bigger model, train longer with better optimization (momentum, RMSprop, Adam), try different NN architecture / hyperparameters.
Q17: Name three variance-reduction techniques.
Get more data, use regularization (L2, dropout, data augmentation), try different NN architecture / hyperparameters.
Q18: What is the weighted-error metric and why is it useful?
It multiplies each example's error by a weight \(w^{(i)}\), so that some mistakes count more than others. Useful when different errors have different real-world costs (e.g., pornographic images).
Q19: Why can a dev set of 100 examples be problematic?
A 0.1% difference between models corresponds to 0.1 examples — not statistically meaningful. You cannot reliably tell which model is better.
Q20: In the medical image example, why is the choice of "human-level" important?
Because the gap between human error and training error determines whether you focus on bias or variance. Using the wrong human reference (e.g., typical human vs. team of experts) changes the diagnosis.

16. Self-Test

Easy

1. What does the chain of assumptions in ML consist of?
Train → dev → test → real world. Each step must be satisfied before the next matters.
2. Define precision in one sentence.
Of all examples predicted positive, the fraction that are actually positive.
3. Define recall in one sentence.
Of all examples that are actually positive, the fraction that were correctly predicted positive.
4. What is the F1 score formula?
\(F_1 = \frac{2}{1/P + 1/R}\)
5. What is the general rule for optimizing vs. satisficing metrics?
1 optimizing metric, \(N-1\) satisficing metrics.

Medium

6. Why is random shuffling into dev/test not always correct?
Because if the data comes from multiple sources with different proportions, random shuffling can produce a dev set that does not match the target deployment distribution (e.g., loan approvals for medium vs. low income).
7. A model has 3% error on dev and 5% error on test. What might be wrong?
The dev and test sets may come from different distributions, or the dev set was overfit to during model selection. The test set is the unbiased final evaluation.
8. Why is human-level performance a proxy for Bayes error?
Because for many natural perception tasks, humans are near the theoretical best possible performance. The best human result gives an upper bound on how good any model can be.
9. If training error is 0.3% and team-of-humans error is 0.5%, what does this tell you?
The model has surpassed human-level performance on the training set. The conventional bias/variance diagnostic (using human error as Bayes proxy) becomes unreliable. You may need other ways to estimate Bayes error.
10. What is the difference between avoidable bias and variance?
Avoidable bias = human error − training error (how much room to improve on training). Variance = training error − dev error (how much the model fails to generalize).

11. You have a dev set of 100 examples. Model A gets 97%, Model B gets 97.1%. Should you switch to B?
No. The difference is 0.1% = 0.1 examples. It is not statistically meaningful. You need a larger dev set to detect such small differences reliably.
12. Your cat classifier has 2% error on dev but users complain it shows inappropriate images. What should you do?
Change the evaluation metric to a weighted error that penalizes inappropriate images much more heavily. Then re-evaluate your models. The metric should rank-order models according to what the application actually cares about.
13. Explain orthogonalization using the TV analogy.
A TV has separate knobs for vertical position, horizontal position, size, and shape. Turning one does not disturb the others. In ML, we want hyperparameters and design choices that each affect one aspect of performance (e.g., bias, variance, data quality), so debugging is tractable.
14. In a medical image classification task, why might you choose "team of experienced doctors" as your human-level reference instead of "typical doctor"?
Because you want your model to perform at the level of the best available human expertise, not just an average doctor. The choice depends on the application goal — replacing a typical doctor vs. beating the best team.
15. You have avoidable bias = 0.2% and variance = 0.1%. What should you focus on?
Both are small. Avoidable bias is slightly larger, so focus on bias reduction first. But the model is already close to optimal; gains will be small.
16. Why is the harmonic mean used in F1 instead of the arithmetic mean?
The harmonic mean is pulled toward the smaller value. If precision is 98% and recall is 10%, the arithmetic mean is 54% (misleadingly okay), but the harmonic mean is ~18% (correctly shows the model is bad).
17. What is the "no test set" pattern and when is it acceptable?
Using the dev set as the final evaluation without a separate test set. Acceptable when data is plentiful, the cost of a wrong decision is low, and you do not need an unbiased final estimate (e.g., online advertising).
18. Explain the four-step chain of assumptions and what to do if step 2 fails.
1. Fit training set well. 2. Fit dev set well. 3. Fit test set well. 4. Perform well in real world. If step 2 fails, the model is overfitting (high variance). Remedies: regularization, more training data, data augmentation.
19. How would you set up dev/test sets for a cat classifier deployed worldwide?
Collect data from all regions where the product is used. Make the dev and test sets come from the same distribution, and make that distribution reflect the expected future deployment data. Consider weighting by region importance if some regions matter more.
20. Why is it important to have a single-number evaluation metric?
It allows fast, unambiguous comparison between models. With multiple metrics, teams waste time arguing about which model is better. A single number speeds up iteration.
