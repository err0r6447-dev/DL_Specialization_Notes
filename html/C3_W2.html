1. Build Your First System Quickly, Then Iterate

🔵 Definition Build-first-then-iterate is a strategy: set up your dev/test sets and metric, build a quick initial model, then use bias/variance and error analysis to decide what to improve next.

1.1 The recommended workflow

  1. Set up dev/test sets and metrics. This defines your target.
  2. Build an initial system quickly.
    • Train on the training set (fit the parameters).
    • Tune on the dev set (tune hyperparameters / model selection).
    • Assess on the test set (final unbiased evaluation).
  3. Use bias/variance analysis and error analysis to prioritize next steps.
🟢 Intuition Building a quick, imperfect system gives you something to measure. Without a baseline, you cannot tell whether a fancy new idea is actually helping. The quick system is a "scaffold" you will improve.
🟡 Important Do not spend weeks perfecting the first model. Get it working end-to-end quickly, then iterate. The dev set + metric tell you where to focus.

1.2 Speech recognition example

Suppose you are building a speech recognition system. Your dev set contains audio from many conditions:

  • Noisy background
  • Café noise
  • Car noise
  • Accent
  • Far from microphone
  • Young speakers
  • Stutter

Instead of trying to fix all of these at once, you build a baseline, measure which categories contribute most to dev error, and tackle the biggest categories first.

2. Carrying Out Error Analysis

🔵 Definition Error analysis is the process of manually examining a sample of misclassified dev examples, categorizing them, and counting how many fall into each category — so you know which problems are worth fixing.

2.1 The cat classifier example

Your cat classifier has 90% accuracy (10% error) on the dev set. You notice it sometimes mistakes dogs for cats. Should you spend months building a "dog detector"?

Here is the key calculation:

  • Current dev error: 10%
  • Fraction of errors that are dogs: 5%
  • If you perfectly fixed all dog errors, new dev error = 10% − (10% × 5%) = 9.5%
🟢 Intuition Error analysis tells you the ceiling on how much a particular fix can help. If fixing dogs can only reduce error from 10% to 9.5%, it is probably not worth months of effort. If it could reduce error from 10% to 3%, it is worth it.

2.2 Evaluating multiple ideas in parallel

Suppose you have several ideas for improving the cat classifier:

  • Fix pictures of dogs being recognized as cats.
  • Fix great cats (lions, panthers) being misrecognized.
  • Improve performance on blurry images.

Create a spreadsheet. For each misclassified dev example, put a checkmark in the columns that apply:

From this table, blurry images (61%) and great cats (43%) are the biggest contributors. That is where you should focus first.

🟡 Important Error analysis is manual work, but it is usually worth a few hours. It prevents you from spending weeks on a fix that only addresses 5% of your errors.

3. Evaluating Multiple Ideas in Parallel

The slide above already introduced the spreadsheet method. Here is a more detailed look at why it works and how to use it.

3.1 The process

  1. Collect ~100 misclassified dev examples.
  2. Define a set of categories (e.g., Dog, Great Cat, Blurry, Instagram filter, …).
  3. For each example, mark which categories apply.
  4. Count the percentage of errors in each category.
  5. Prioritize the categories with the highest percentages.
🔴 Warning — Categories can overlap A single image can be both blurry and a dog. That is fine. The percentages will not sum to 100%, and they should not. You are measuring how often each problem appears, not partitioning the errors.

3.2 What you learn

  • Which problems are most common (biggest potential impact).
  • Which problems are rare (probably not worth fixing yet).
  • Whether a proposed fix has a reasonable ceiling.

4. Cleaning Up Incorrectly Labeled Data

🔵 Definition Incorrectly labeled examples are training/dev/test examples whose label \(y\) is wrong — for example, a dog image labeled as a cat, or a cat image labeled as "not cat".

4.1 Training set: random vs. systematic errors

🟢 Intuition Deep learning algorithms are surprisingly robust to random label errors in the training set. But they are not robust to systematic errors.

Random errors: a few cats mislabeled as dogs, scattered randomly. The model sees mostly correct examples and learns the right pattern.

Systematic errors: all white cats labeled as dogs. The model learns the wrong pattern. This is much more harmful.

4.2 Dev/test set: error analysis with "incorrectly labeled" column

Add an "Incorrectly labeled" column to your error-analysis spreadsheet:

ImageDogGreat CatBlurryIncorrectly labeledComments
98✓Labeler missed cat in background
99✓
100✓Drawing of a cat; not a real cat
% of total8%43%61%6%

Now you can compute:

  • Overall dev error: 10%
  • Errors due to incorrect labels: 10% × 6% = 0.6%
  • Errors due to other causes: 10% − 0.6% = 9.4%
🟡 Important If incorrect labels account for only 0.6% of your 10% error, fixing labels will not help much. Focus on the other 9.4%. But if incorrect labels were, say, 3%, they might be worth fixing.

4.3 Correcting dev/test set examples

  • Apply the same process to dev and test sets. If you fix incorrect labels in dev but not test, they will come from different distributions.
  • Consider examining examples your algorithm got right as well as wrong. There may be mislabeled examples that the model happens to classify correctly — fixing them prevents future confusion.
  • Train and dev/test data may now come from slightly different distributions. Be aware of this; it is usually acceptable, but keep it in mind when interpreting results.
🔴 Warning Do not spend days manually fixing labels unless error analysis shows that incorrect labels are a significant contributor. It is easy to get sucked into label-cleaning when the real problem is elsewhere.

5. Training and Testing on Different Distributions

🔵 Definition Data mismatch occurs when your training set comes from a different distribution than your dev/test sets (and the real-world data you care about).

5.1 The cat mobile app example

You are building a mobile app that classifies cat photos uploaded by users. You have two data sources:

  • Web data: 200,000 professionally shot, high-resolution cat images.
  • App data: 10,000 amateur photos — blurry, poorly framed, taken by users.

The app data is what you actually care about. But it is small. The web data is large but from a different distribution.

5.2 Option 1 (bad): shuffle everything together

Mix all 210,000 images and randomly split into train/dev/test.

  • Train: 205,000 (mostly web)
  • Dev: 2,500 (mostly web)
  • Test: 2,500 (mostly web)
🔴 Warning This is bad because your dev/test sets are dominated by web images. You will optimize for web performance, but your app users upload amateur photos. The dev set does not reflect what you care about.

5.3 Option 2 (good): make dev/test reflect the target

Put all 200,000 web images in the training set. Split the 10,000 app images into 5,000 dev and 5,000 test. Optionally, add a few app images to training.

🟡 Important Advantage: the target (what you care about) is well defined.
Disadvantage: training distribution differs from dev/test. But this is usually worth it — long-term performance is better when you optimize for the right distribution.

5.4 Speech recognition example

You are building a speech-activated rearview mirror. You have:

  • 500,000 training examples from purchased data, smart speaker control, voice keyboard.
  • 10,000 examples from the rearview mirror (what you care about).

Split: 500k+10k train (or 510k train), 5k dev, 5k test — with dev/test from the rearview mirror distribution.

🟢 Intuition Always ask: "What data will my model see in deployment?" That is the distribution your dev and test sets should reflect. Training can include other data to help the model learn general features, but dev/test must match the target.

6. Bias & Variance with Mismatched Data Distributions

🔵 Definition — Training-dev set A training-dev set has the same distribution as the training set, but is not used for training. It lets you separate "variance" from "data mismatch".

6.1 Why the standard bias/variance analysis breaks

Normally:

  • Human error − training error = avoidable bias
  • Training error − dev error = variance

But when train and dev come from different distributions, the gap between training error and dev error mixes two things:

  1. The model failing to generalize to new examples (variance).
  2. The dev set containing examples from a different, possibly harder distribution (data mismatch).

6.2 The new diagnostic table

MetricWhat it measures
Human error (≈ Bayes)Best possible
Training errorFit on training distribution
Training-dev errorGeneralization within training distribution
Dev errorPerformance on target distribution
Test errorFinal unbiased performance on target distribution

The gaps are interpreted as:

  • Avoidable bias = Human error − Training error
  • Variance = Training error − Training-dev error
  • Data mismatch = Training-dev error − Dev error
  • Degree of overfitting to dev = Dev error − Test error

6.3 The six scenarios

Scenario A: Training error 1%, training-dev 9%, dev 10%. The gap between training and training-dev is 8% → variance problem. (The gap between training-dev and dev is only 1% → little data mismatch.)

Scenario B: Training 1%, training-dev 1.5%, dev 10%. Variance = 0.5% (small). Data mismatch = 1.5% − 10% = −8.5%? Wait, let's recompute: training-dev 1.5% to dev 10% is a gap of 8.5% → data mismatch problem.

Scenario C: Training 1%, training-dev 1.5%, dev 10%. Same as B — data mismatch.

Scenario D: Training 10%, training-dev 11%, dev 12%. Avoidable bias = 10% (large). Variance = 1%. Data mismatch = 1%. → Bias problem.

Scenario E: Human 4%, training 7%, training-dev 10%, dev 20%. Avoidable bias = 3%. Variance = 3%. Data mismatch = 10%. → Bias + variance + data mismatch (multiple problems).

Scenario F: Dev 6%, test 6%. Dev and test match. No overfitting to dev.

🟡 Important Development should never be done on the test set — use dev for iteration, test only for final evaluation. The difference between dev and test error tells you how much you have overfit to the dev set.

7. Addressing Data Mismatch

🟡 Guideline
  1. Carry out manual error analysis to understand the difference between training and dev/test sets.
  2. Make training data more similar; or collect more data similar to dev/test sets.
  3. Use artificial data synthesis if needed — but be careful.

7.1 Manual error analysis

Compare training errors and dev errors on the same categories. For example:

  • Noisy background: training error 2%, dev error 10% → mismatch here.
  • Car noise: training error 5%, dev error 6% → less mismatch.
  • Street numbers: training error 8%, dev error 9% → not the main issue.

This tells you which aspects of the distribution differ, so you can target them.

7.2 Collect more data similar to dev/test

If error analysis shows that car noise is the problem, collect more car-noise audio and add it to training. This is often the most reliable fix.

8. Artificial Data Synthesis

🔵 Definition Artificial data synthesis is the process of generating new training examples by combining or transforming existing data — for example, adding car noise to clean audio.

8.1 Audio example

You have 10,000 hours of clean audio ("The quick brown fox jumps over the lazy dog") and only 1 hour of car noise. You can synthesize in-car audio by adding the car noise to the clean audio.

8.2 Car recognition example

You have 1,000 images of a car. You can synthesize more by applying transformations: change lighting, change background, rotate, crop, etc. This gives you many more training examples from a small set.

🔴 Warning — The tiny-subset trap Artificial synthesis can accidentally create data from only a tiny subset of the space of all possible examples. For example, if you only have 1 hour of car noise, your synthesized in-car audio may not represent all car noises. The model may overfit to that one noise type. Always check whether your synthesized data covers the full range of real-world variation.

9. Transfer Learning

🔵 Definition Transfer learning means using knowledge learned from one task (Task A) to help learn a different task (Task B). You "pre-train" on Task A, then "fine-tune" on Task B.

9.1 Cat recognition → radiology diagnosis

Suppose you have a neural network trained for cat recognition (image → cat / not cat). You want to build a radiology diagnosis model (X-ray image → malignant / benign).

9.2 How to do it

  1. Take the pre-trained network (trained on Task A).
  2. Delete the last output layer and the weights feeding into it.
  3. Create a new set of randomly initialized weights for the new output layer.
  4. Train on the new dataset \((x, y)\) for Task B.

You can either:

  • Freeze the earlier layers and only train the new output layer (if Task B data is small).
  • Fine-tune all layers with a small learning rate (if Task B data is larger).

9.3 When transfer learning makes sense

  • Task A and Task B have the same input \(x\) (e.g., both are images).
  • You have a lot more data for Task A than Task B.
  • Low-level features from Task A could be helpful for Task B.
🟣 Example — Speech recognition Pre-train on 10,000 hours of speech recognition. Fine-tune on 1 hour of wake-word detection ("Hey device…"). The low-level audio features transfer well.
🟡 Important Transfer learning is one of the most powerful practical tools in deep learning. It lets you build good models even when your target task has limited data.

10. Multi-Task Learning

🔵 Definition Multi-task learning means training one neural network to do several tasks simultaneously, sharing lower-level features.

10.1 Autonomous driving example

A self-driving car must detect:

  • Pedestrians
  • Cars
  • Road signs (stop signs)
  • Traffic lights

Instead of training four separate networks, train one network with four outputs.

10.2 The output vector

Each training example \(x^{(i)}\) is an image with multiple labels:

\[ y^{(i)} = \begin{bmatrix} 0 \\ 1 \\ 1 \\ 0 \end{bmatrix} \begin{array}{l} \text{Pedestrians} \\ \text{Cars} \\ \text{Road signs – Stop} \\ \text{Traffic lights} \end{array} \]

Unlike softmax regression (where labels are mutually exclusive), multi-task learning allows multiple labels to be 1 at the same time. For example, an image can contain both a car and a stop sign.

10.3 The loss function

\[ J = -\frac{1}{m} \sum_{i=1}^{m} \sum_{j=1}^{4} \left[ y_j^{(i)} \log(\hat{y}_j^{(i)}) + (1 - y_j^{(i)}) \log(1 - \hat{y}_j^{(i)}) \right] \]
\(m\) = number of training examples.
\(j\) = task index (1 to 4).
\(y_j^{(i)}\) = true label for task \(j\) on example \(i\).
\(\hat{y}_j^{(i)}\) = predicted probability for task \(j\) on example \(i\).
The inner sum is the logistic loss for each task; the outer sum averages over examples.

If some examples have missing labels for some tasks (e.g., a traffic-light label is unknown), you can simply sum only over the labeled \(j\) values. The loss is not affected by unlabeled entries.

10.4 When multi-task learning makes sense

  • Tasks share lower-level features.
  • The amount of data for each task is roughly similar.
  • You can train a big enough network to do well on all tasks.
🟡 Important Multi-task learning is used less often than transfer learning in practice, but it is very useful when you have multiple related tasks and enough data for each.

11. End-to-End Deep Learning

🔵 Definition End-to-end deep learning means replacing a multi-stage pipeline with a single neural network that maps \(x\) directly to \(y\).

11.1 Speech recognition example

Traditional pipeline:

  • Audio → MFCC features → phonemes → words → transcript

End-to-end:

  • Audio → transcript (one network)

11.2 Other examples

  • Face recognition: Image → identity (end-to-end), vs. image → detect face → zoom → compare (pipeline).
  • Machine translation: English → French (end-to-end), vs. English → text analysis → … → French (pipeline).
  • Child age estimation: X-ray image → age (end-to-end), vs. image → bones → age (pipeline).
🔴 Warning End-to-end learning needs a lot of labeled data. It is not suitable for every problem. If your dataset is small, a pipeline with hand-designed components may work better.

12. Whether to Use End-to-End Learning

🔵 Key question Do you have enough data to learn a function of the complexity needed to map \(x\) to \(y\)?

12.1 Pros

  • Let the data speak. The network learns from \(x\) to \(y\) directly, rather than being forced to reflect human preconceptions.
  • Less hand-designing of components. It simplifies the design workflow.

12.2 Cons

  • May need a large amount of labeled data. It cannot be used for every problem.
  • Excludes potentially useful hand-designed components. Data and hand-designed features are the two main sources of knowledge for a learning algorithm. If the dataset is small, hand-designed components can inject useful manual knowledge.
🟣 Example — Autonomous driving Pipeline: image + radar + lidar → car detection (DL) → pedestrian detection (DL) → motion planning → route → steering control.
End-to-end: image → steering.
In practice, a hybrid approach is often best: use DL for perception (car/pedestrian detection) and traditional methods for motion planning and control, because data for the intermediate steps is easier to collect.
🟡 Important Choose the architecture based on what data you can get. If you have lots of \((x, y)\) pairs for the full task, end-to-end may work. If you have data for intermediate steps but not the full task, a pipeline is better.

13. Weekly Summary

🔵 Key Concepts
  • Build first, iterate later. Set up dev/test + metric, build a quick baseline, then diagnose.
  • Error analysis: manually examine ~100 errors, categorize, count.
  • Parallel evaluation: spreadsheet with categories to prioritize fixes.
  • Incorrect labels: random errors are tolerable; systematic errors are harmful.
  • Data mismatch: train and dev/test from different distributions.
  • Training-dev set: same distribution as training, not used for training — separates variance from mismatch.
  • Artificial data synthesis: generate more training data, but watch for the tiny-subset trap.
  • Transfer learning: pre-train on Task A, fine-tune on Task B.
  • Multi-task learning: one network, multiple tasks, shared features.
  • End-to-end learning: one network from x to y; needs lots of data.

Important Equations

EquationMeaning
Avoidable bias ≈ Human error − Training errorHow much bias you can still remove.
Variance ≈ Training error − Training-dev errorGeneralization within training distribution.
Data mismatch ≈ Training-dev error − Dev errorHow different the target distribution is.
\(J = -\frac{1}{m}\sum_{i=1}^{m}\sum_{j=1}^{4}[y_j^{(i)}\log\hat{y}_j^{(i)} + (1-y_j^{(i)})\log(1-\hat{y}_j^{(i)})]\)Multi-task learning loss (logistic loss summed over tasks).

Common Confusions

  • Variance vs. data mismatch: variance = same distribution, new examples; mismatch = different distribution.
  • Transfer vs. multi-task: transfer = sequential (A then B); multi-task = simultaneous (A and B together).
  • Random vs. systematic label errors: random is tolerable; systematic is harmful.
  • End-to-end vs. pipeline: end-to-end needs more data; pipeline allows hand-designed components.

14. Quick Review (with answers)

Q1: What is the recommended workflow for starting a new ML project?
Set up dev/test sets and metrics, build an initial system quickly, then use bias/variance and error analysis to prioritize next steps.
Q2: What is error analysis?
Manually examining ~100 misclassified dev examples, categorizing them, and counting how many fall into each category to decide which problems are worth fixing.
Q3: In the cat classifier example, if 5% of errors are dogs and dev error is 10%, what is the ceiling if you fix all dog errors?
New dev error = 10% − (10% × 5%) = 9.5%. So the best possible improvement from fixing dogs is 0.5%.
Q4: What is the difference between random and systematic label errors?
Random errors are scattered and the model is robust to them. Systematic errors follow a pattern (e.g., all white cats labeled as dogs) and teach the model the wrong rule.
Q5: What is a training-dev set and why is it useful?
A training-dev set has the same distribution as the training set but is not used for training. It lets you separate variance (training → training-dev gap) from data mismatch (training-dev → dev gap).
Q6: What does the gap between training-dev error and dev error represent?
Data mismatch — how much worse the model does on the target distribution compared to the training distribution.
Q7: What is the tiny-subset trap in artificial data synthesis?
Synthesizing data from only a small subset of the real-world variation (e.g., 1 hour of car noise) can cause the model to overfit to that subset rather than generalizing.
Q8: What is transfer learning?
Using knowledge learned from Task A to help learn Task B. You pre-train on Task A, then replace the output layer and fine-tune on Task B.
Q9: When does transfer learning make sense?
When Task A and B have the same input x, you have more data for A than B, and low-level features from A are helpful for B.
Q10: What is multi-task learning?
Training one neural network to do several tasks simultaneously, sharing lower-level features. Each output head predicts a different label.
Q11: How does the multi-task loss function differ from softmax regression?
In softmax regression, labels are mutually exclusive (one correct class). In multi-task learning, multiple labels can be 1 at the same time (e.g., a car and a stop sign in the same image).
Q12: When does multi-task learning make sense?
When tasks share lower-level features, you have roughly similar amounts of data for each task, and you can train a big enough network.
Q13: What is end-to-end deep learning?
Replacing a multi-stage pipeline with a single neural network that maps x directly to y.
Q14: What is the key question to ask before using end-to-end learning?
Do you have enough data to learn a function of the complexity needed to map x to y?
Q15: What are the pros and cons of end-to-end learning?
Pros: lets the data speak, less hand-designing. Cons: needs large amounts of labeled data, excludes potentially useful hand-designed components.
Q16: In the loan approval example, why is random shuffling into dev/test problematic?
Because if the data comes from different income-level zip codes, random shuffling can produce a dev set dominated by one type, not matching the target distribution.
Q17: What is the correct way to split data when train and target distributions differ?
Put most of the large-distribution data in training, but make dev and test come from the target distribution you care about.
Q18: How do you handle missing labels in multi-task learning?
Sum the loss only over the tasks j that have labels for that example. Unlabeled entries do not affect the loss.
Q19: Why is dev set error vs. test set error important?
The gap between them tells you how much you have overfit to the dev set. Development should never be done on the test set.
Q20: Give an example of a problem where ML significantly surpasses human-level performance.
Online advertising, product recommendations, logistics (predicting transit time), loan approvals — structured data problems.

15. Self-Test

Easy

1. What are the three steps of the build-first-then-iterate workflow?
1. Set up dev/test sets and metrics. 2. Build an initial system quickly. 3. Use bias/variance and error analysis to prioritize next steps.
2. What is error analysis in one sentence?
Manually examining misclassified dev examples, categorizing them, and counting how many fall into each category.
3. What does a training-dev set measure?
Generalization within the training distribution (variance), separate from data mismatch.
4. Define transfer learning.
Using knowledge learned from Task A to help learn Task B by pre-training and fine-tuning.
5. Define multi-task learning.
Training one neural network to do several tasks simultaneously, sharing lower-level features.

Medium

6. You have 10% dev error and find that 20% of errors are blurry images. What is the ceiling if you fix all blurry errors?
New dev error = 10% − (10% × 20%) = 8%. The maximum improvement is 2%.
7. Training error = 1%, training-dev error = 9%, dev error = 10%. What is the diagnosis?
Variance problem (1% → 9% gap is large). Data mismatch is small (9% → 10%). Focus on variance reduction.
8. Training error = 1%, training-dev error = 1.5%, dev error = 10%. What is the diagnosis?
Data mismatch problem (1.5% → 10% gap is large). Variance is small. Focus on making training data more similar to dev.
9. Why is random label noise in the training set less harmful than systematic label noise?
Random noise is scattered and the model learns the correct pattern from the majority of correct examples. Systematic noise teaches the model a wrong rule.
10. What is the "tiny-subset trap" in artificial data synthesis?
Synthesizing data from a small subset of real-world variation can cause overfitting to that subset. Always check coverage.

Hard

11. You have a cat classifier with 5% dev error. 10% of errors are dogs, 30% are blurry, 40% are great cats. What should you focus on?
Great cats (40%) and blurry images (30%) are the biggest categories. Fixing great cats could reduce error by up to 2% (5% × 40% = 2%); blurry by 1.5%. Focus on great cats first.
12. In the speech recognition example, why is dev/test from the rearview mirror distribution even though most data comes from other sources?
Because the rearview mirror is the target application. Dev/test must reflect the data you expect in deployment, not the data that is easiest to collect.
13. You have 200k web cat images and 10k app images. Design the train/dev/test split and explain why.
Training: 200k web + 5k app (205k total). Dev: 5k app. Test: 5k app. Dev/test must come from the target distribution (app) so you optimize for what matters.
14. Explain the difference between transfer learning and multi-task learning.
Transfer learning is sequential: train on Task A, then fine-tune on Task B. Multi-task learning is simultaneous: one network trained on Tasks A, B, C, D at the same time.
15. Why does end-to-end learning need more data than a pipeline?
Because it must learn the entire mapping from x to y without hand-designed intermediate representations. The pipeline injects human knowledge at each stage, reducing what the model needs to learn.
16. You have 1 hour of car noise and 10,000 hours of clean speech. What is the risk of synthesizing in-car audio?
The synthesized audio may only cover the specific car noise in that 1 hour. The model may overfit to that noise type and fail on other car noises. Collect more diverse noise if possible.
17. In multi-task learning, what happens if some examples have missing labels?
You sum the loss only over the tasks that have labels for that example. Unlabeled entries do not contribute to the loss.
18. Why is dev/test set error vs. training-dev error important for diagnosing data mismatch?
Training-dev error shows performance on the training distribution (unseen examples). Dev error shows performance on the target distribution. The gap between them isolates data mismatch from variance.
19. A model has training error 0.3%, training-dev error 0.5%, dev error 0.6%, human error 0.5%. What is the diagnosis?
Avoidable bias is small (0.5% − 0.3% = 0.2%). Variance is small (0.3% → 0.5% = 0.2%). Data mismatch is small (0.5% → 0.6% = 0.1%). The model is close to human level; gains will be small.
20. You have a small target dataset and a large related dataset. Should you use transfer learning, multi-task learning, or end-to-end learning? Why?
Transfer learning. You pre-train on the large dataset (Task A) and fine-tune on the small target dataset (Task B). Multi-task learning needs similar amounts of data for all tasks; end-to-end needs a large target dataset.
